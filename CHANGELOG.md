# История изменений

## 2.2

Серверное копирование объектов и параллельная передача частей.

### Копирование объектов

- `IObjectBucket<TMetadata, TKey>.CopyToAsync(...)` — копия силами хранилища (S3 `CopyObject`), байты не проходят через приложение. Метаданные копии пишутся заново, поэтому у цели могут быть свой тип метаданных и свой тип ключа. `false`, если исходного объекта нет.
- `IObjectStorageContext.CopyAsync<TSource, TTarget>(...)` — фасад для случая «оба бакета в одном хранилище, ключи `Guid`». На `ObjectStorageContext` есть перегрузка с типизированными ключами.
- Без `UploadOptions` переносятся все системные заголовки источника, включая `Content-Encoding`, `Content-Language` и `Expires`.
- Объекты больше 5 ГБ копируются многочастно, диапазонами. Каждая часть привязана к ETag источника: перезапись источника по ходу копирования роняет операцию (412), а не склеивает копию из двух версий.
- Оба бакета должны принадлежать одному подключению, иначе `InvalidOperationException`. Фолбэка «прочитать и залить» нет.
- Фейк из `.Testing` поддерживает копирование; расхождения перечислены в README, раздел «Тестирование».

### Параллельная передача частей

- Новая опция `ObjectStorageOptions.MultipartParallelism` (по умолчанию `1`, потолок 64) — сколько частей передаётся одновременно, при загрузке и при копировании.
- Дефолт `1` оставляет расход памяти прежним. Параллелизм включается осознанно: под каждую часть в полёте нужен свой буфер, и это умножается на число одновременных загрузок. У серверной копии буферов нет, там параллелизм бесплатный.
- Внутренний путь multipart-загрузки переписан под пул буферов. При `MultipartParallelism = 1` поведение то же, что и раньше: один буфер, части по очереди.

### Совместимость

- Для вызывающего кода изменения аддитивные.
- В `IObjectBucket<TMetadata, TKey>` и `IObjectStorageContext` добавлены члены без реализации по умолчанию: внешние реализации этих интерфейсов (самописные дубли, декораторы) перестанут компилироваться, пока их не добавят.
